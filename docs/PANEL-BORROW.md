# 面板参考：这张截图里有什么值得抄

> 分析对象：用户提供的多任务线 Agent 客户端截图（2400×1080）
> 结论：**它的底层模型比我的 v0.1 更接近"真实工作发生过什么"**。我采纳 5 条，否决 3 条，并做了一张由账本直接渲染的图来验证。

---

## 1. 先解码：这张图到底是什么

三栏布局，每栏解决一个不同的问题：

| 区域 | 内容 | 它在回答的问题 |
|---|---|---|
| 左栏 | 工作树 → 会话列表；每项带 `wt/douyin-dl` 分支名、状态点、`2/5` 完成度 | 我手上有几条任务线，各自跑到哪了 |
| 中栏 | 会话流：`交接 → Grok · 8.8K+8.8K · 2步 · 1s`、可折叠的步骤块（读文件 1s / 跑 ffmpeg 6s / 镜头检测 11s）、产物内联预览（关键帧时间轴）、总结 | 这个人具体在干什么，每一步花了多久 |
| 右栏 | **泳道提交图**：每列一条车道，节点是提交/交接/门禁/重试/压缩，边是血缘；底部 15 种图例 | 谁基于谁的什么版本往下做，哪里分叉、哪里退回 |

关键洞察：**它的主视图不是"组织架构图"，也不是"甘特图"，而是一张 git 风格的提交图。** 每个 Agent 的产出 = 一次 commit；交接 = 一次显式事件并带 token 成本；分叉、合并、重试、等待审核都是一等公民。

我以前的面板（v0.1）用的是**固定流水线 DAG**——那是"计划"，而这张图是"实际发生过的"。两者应该是两层，不是一个。

---

## 2. 值得采纳的 5 条

### ① 泳道提交图替代固定 DAG（采纳，最高优先）

我的 S1→S6 是设计时画死的。但真实流程一定会出现：审计退回、个股重写、版本分叉、两个文件合并成终稿。这些在固定 DAG 里只能显示成"节点变红"，在图里则是**真实的分支与合并**。

而且它和我的架构天然吻合：`events.jsonl` 里每条事件本来就有 `seq` 和 `ts`，加上 `payload.parents` 就能直接构图。**面板不需要新数据源，只需要多一个投影器。**

已经验证：`docs/lane-graph.png` 就是把 `runtime/ledger/sample-case-2026-001.jsonl` 直接渲染出来的（`scripts/render_lane_graph.py`，坐标全部来自事件时间戳）。

### ② 显式的"交接"事件 + 成本计量（采纳）

截图里 `交接 → Grok · 8.8K + 8.8K · 2 步 · 1s` 一行信息量很大：交给谁、双方上下文多大、几步、多久。

我的设计里"交接"是隐式的——B 排队拿到锁、读文件，就算交接完了。这丢失了三件事：**上下文是怎么传的、传了多少、传的时候有没有丢东西**。改成显式 `handoff` 事件后，顺带解决了"审计质疑某条结论是谁的责任"这个扯皮问题。

### ③ 上下文压缩是可见状态（采纳）

截图车道状态里有 `3/6 · 上下文压缩`。我原来完全没考虑：6 个 Agent、每人读 4~6 份文件，上下文一定会爆，一爆就开始丢细节、开始编。

补一条 `context.compacted` 事件，面板上显示"压缩 68K→12K"。这不是装饰——它告诉你**这份底稿的质量可能在那里掉了**，值得你在面板上点开看一眼。

### ④ 员工纵深轨迹（采纳，但降级为抽屉）

中栏的步骤块（可折叠、带耗时、带产物预览）是我 v0.1 缺的：我有"事件流"（全局）和"员工卡"（当前状态），但没有"点开某个人看他今天的完整时间线"。

采纳为**抽屉**而不是主视图：主视图仍是泳道图 + 锁队列，点节点/点卡片才展开这个人的轨迹。理由：你是监督者，先看"哪里卡住了"，再看"他卡在哪一步"。

### ⑤ 图例即状态词表（采纳）

它底部 15 种节点类型（提交/测试/产物/等待你/交接/审查通过/工具调用/跨线引用/检查点/分叉/模型切换/上下文压缩/合并/错误/重试）本质上是一份**状态词汇表**。我的事件表只有 11 种，缺 `handoff / context.compacted / retry / merge / cross_ref`，已经补进 DESIGN.md §5。

## 3. 不能照抄的 3 条

### ① 它是"隔离"，我是"排队"——这是根本分歧

它每条任务线一个 **git worktree**（分支名都写在左边栏 `wt/douyin-dl`），各自有独立工作副本，**根本不会争用同一个文件**，合并在最后显式发生。

我的方案是反过来的：所有人共享同一份文件，靠 FIFO 排队。

**两者不是谁对谁错，而是取舍不同：**
- 隔离：无争用、可并行、可回滚；代价是"最新版在哪"需要合并，且合并本身要人（或 Lead）来判。
- 排队：只有一份真相、永远没有合并冲突；代价是串行等待、吞吐受限。

**建议采用双轨制**（这条改动我认为是本次最有价值的）：

| 层 | 机制 | 放什么 |
|---|---|---|
| 草稿层 | 每人一个 `drafts/<agent>/`（worktree 语义），**不排队**，随便写 | 分析笔记、中间计算、被他退回的旧稿 |
| 交付层 | `vault/` 共享，**严格排队 + 版本 CAS** | 阶段正式产出（research/*.md、review/*、final_report） |

这正好解决我 v0.1 里自己提的那个风险——"6 个 Agent 为看一眼互相排队，流水线退化成串行"。排队应该只发生在**交付物**上，不该发生在**草稿**上。

### ② 它的"人"是主体，我的"文件"是主体

截图里一切围绕"会话/人"组织；我的方案围绕"文件与门禁"组织（因为你要的是共享文件 + 排队）。照搬会把"谁卡在哪个文件、队位第几、等了多少秒"这些**你真正要看的信息**挤掉。

**保留**锁队列看板作为主视图的一半，与泳道图并排。

### ③ 成本指标不能只抄 token

它显示 token 成本，因为模型切换要算钱。我的流水线里**等待时间才是瓶颈**（一个底稿写 50 秒，法律顾问干等 25 秒）。所以我的指标应该是：等待时长 / 持锁时长 / 有效工作时间，三个一起看。只显示 token 会误导你优化错方向。

## 4. 落地：面板 v2 三视图

```
┌──────────┬───────────────────────────────────────┬──────────────┐
│ 任务线    │  泳道提交图（默认主视图）                │ 锁队列 + 告警 │
│ case-001 ●│  ├ 宏观 ▓▓▓                            │ stock.md v2  │
│ case-002 ●│  ├ 行业    ▓▓▓                          │  hold stock  │
│          │  ├ 个股       ▓▓▓▓ ←退回→ ▓▓            │  剩 47s      │
│ 每行显示  │  ├ 审计          ▓  ✗fail               │  #1 audit 17s│
│ 完成度    │  └ 交付            ▲等待你               │  #2 legal 25s│
├──────────┴───────────────────────────────────────┴──────────────┤
│ 点击节点 → 抽屉：该员工的步骤轨迹 · 该文件的版本 diff · 门禁判定详情 │
└─────────────────────────────────────────────────────────────────┘
```

原有的"员工卡片 + 甘特"降级为泳道图的替代视图（可切换），因为泳道图已经包含了"谁在什么时候占着什么"的信息。**默认视图从"卡片墙"改成"图"——这是对监督者更高效的界面。**

## 5. 与 v0.1 的差异清单

| 项 | v0.1 | 现在 |
|---|---|---|
| 主视图 | 固定流水线 DAG + 员工卡 | 泳道提交图（计划 DAG 作为底纹或单独 tab） |
| 任务线 | 单 case | 多 case 并行（左栏导航） |
| 交接 | 隐式（排队即交接） | 显式 handoff 事件 + 成本 |
| 上下文 | 未考虑 | context.compacted 事件 + 面板提示 |
| 员工纵深 | 员工卡（当前状态） | + 可展开的步骤轨迹抽屉 |
| 文件争用 | 全部排队 | **双轨：草稿隔离 / 交付排队** |
| 指标 | 无 | 等待时长 / 持锁时长 / 有效工作时长 |

---

## 6. 一句话总结

这张截图教我的是：**别把"工作流"画成流程图，要画成"工作真的发生过的那张图"。**
流程图是给老板汇报用的，提交图是给监督者查案用的。你要查的是谁的活卡住了。
