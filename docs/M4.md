## 3. 这次验证到了什么

1. **排队机制在真实竞争下生效**：行业研究员想读宏观底稿时，宏观正持写锁 → 排队 → 超时 → 退避重试 → 拿到读锁。全程没有绕过。
2. **协议能被 LLM 遵守**：两个 agent 都先 acquire 再写、写后自动释放、没有直接写 vault。
3. **自纠错**：宏观研究员发现正文 307 字超了「300 字以内」，主动重新加锁压缩到 297 字出 v2。
4. **版本与历史**：vault 里 macro v2 / industry v1，history 保留 3 个版本（v1、v2、industry v1）。
5. **门禁可执行**：两位都上报了 G-DATA pass 并附依据。

## 4. 这次暴露的问题

1. **门禁状态是单槽**：`gates[G-DATA]` 一个 case 只有一个格子，两个人先后 pass 会互相覆盖（最后 by=industry）。应按 (gate, 报告) 或 (gate, 产物路径) 分开存。
2. **模型配置仍是装饰**：teammate 实际模型是 DSH 运行时给的 deepseek-v4.1-flash，面板左下角切的模型没有传给运行时。
3. **技能没被真正加载**：本轮没有任何 skill.loaded 事件——技能目录/装配是 Broker 里的元数据，agent 侧没有 skill 工具在用。
4. **只跑了 2/6 个角色**：审计、法律、交易员、Lead 汇编都没跑；没有终稿。

## 5. 下一步

1. 修门禁键（gate, scope），否则多报告并行必然互相覆盖；
2. 把面板模型配置接到 teammate 运行参数上；
3. 装满 6 个角色跑一条完整流水线，产出 final_report.md；
